# 01 · 设计说明

> 目标读者：以后要改这个程序（或者照这个套路做下一个桌面小挂件）的人。
> 本文只讲「为什么这么做」，操作层面看 `README.md`。

---

## 一、约束与目标

需求一开始就钉死了四条硬约束，它们决定了后面所有技术选择：

1. **单 exe**，拷过去双击就能用；
2. **不能让人先装运行时**（.NET 6/8、Node、Electron 运行时都不行）；
3. 常驻，**内存要低、空闲 CPU 要接近 0**（它一直贴在屏幕上）；
4. 只读接口，**不得内置任何能花钱的 key**。

另外自带两个软约束：外观要「好看、不土」，行为要「不打扰用户」（不弹窗、抢焦点、丢数据）。

## 二、技术选型

| 方案 | 结论 | 原因 |
|---|---|---|
| **C# WinForms + 系统自带 csc.exe** | ✅ 采用 | .NET Framework 4.8 是 Win10 内置，`csc.exe` 也在系统目录里，**编译即单文件**，不需要 SDK/打包器，产物是纯托管 PE，杀软误报面最小 |
| .NET 6/8 单文件发布 | ❌ | 要么要求目标机装运行时，要么自包含后体积 60–150 MB，且 `PublishSingleFile` 要 SDK |
| Electron / Tauri | ❌ | 体积、内存、打包复杂度全部超标；Tauri 还要 Rust 工具链 |
| PowerShell + WinForms 打成 exe | ❌ | 打包器（ps2exe 之类）极易被 Defender 误报 |
| C++ / Win32 原生 | ❌ | 体积最小但开发成本高，字体与 JSON 都要自己搭 |

关键决策：**不用控件，全部自绘（GDI+）**。一个球/一条栏如果堆 Label+Panel，句柄多、闪烁、半透明难做、缩放会错位；自绘只有一次 `UpdateLayeredWindow`，没有任何子窗口。

## 三、进程与对象结构

一个进程，没有依赖注入、没有插件化，全部在 `GWQuota.cs` 一个文件里（约 2900 行，24 个类型），按职责分层：

```
Program          入口：单实例 Mutex、DPI、异常兜底、Application.Run(AppHost)
  └ AppHost      ApplicationContext，装配与调度中心
      ├ WidgetForm    悬浮窗（球/条，逐像素透明）
      ├ DetailForm    悬停详情面板（不透明窗口）
      ├ NotifyIcon    托盘图标 + 菜单
      ├ Poller        后台线程轮询（自带退避策略）
      └ WinTimer ×3   悬停轮询 / 顶层重申 / 慢速 UI 刷新
数据层：Snapshot / Balance / QuotaWindow / ModelRow + QuotaParser(JavaScriptSerializer)
基础层：Consts / Native / AppPaths / ColorUtil / Gfx / Theme / Palettes / Config / Tz / J
```

三个设计取舍：

- **AppHost 当调度中心**：窗口之间不互相引用，全部通过 `AppHost` 的属性（`Last` 快照、`State` 状态）读数据，避免循环引用。
- **数据不可变**：`Snapshot` 每次拉取新建一个，成功后整体替换。界面永远读一个完整快照，不会出现「余额是新的、百分比是旧的」这种撕裂。
- **失败不清空**：拉取失败只改 `State`，`Last` 保留上一次成功的快照——这是「不打扰用户」的核心。

## 四、渲染管线（这次最费劲的部分）

### 4.1 为什么放弃 Region + Opacity

第一版用「无边框窗体 + `SetWindowRgn` 圆形裁切 + `Form.Opacity`」。两个致命缺点：

- 边缘是**硬切**的，放大看有锯齿，投影做不出来；
- `Form.Opacity` 是**整窗统一 alpha**，调低透明度时文字跟着变淡——用户直接反馈「看不清」。

### 4.2 现在的做法：`UpdateLayeredWindow`

```
Graphics 画到 32bppPArgb 位图（预乘 alpha）
      ↓ LockBits 拷进 CreateDIBSection 的像素内存
      ↓ UpdateLayeredWindow(hwnd, …, AC_SRC_ALPHA, SourceConstantAlpha=255)
系统按每像素 alpha 合成到桌面
```

要点与坑：

| 点 | 说明 |
|---|---|
| **必须是 PArgb** | `UpdateLayeredWindow` 要求**预乘 alpha**。用普通 `Format32bppArgb` 会在半透明边缘出现亮边/灰边。 |
| 窗口 alpha 给 255 | 整窗 alpha 会连带文字一起变淡。所以整窗恒 255，**半透明只画在背景那一层**（`ColorUtil.A(th.Top, bgA)`），文字用原始色。 |
| 鼠标穿透自动生效 | alpha=0 的像素系统不做命中测试，「投影留白」不会挡住背后的窗口。 |
| 需要自管 GDI 对象 | `CreateCompatibleDC` / `CreateDIBSection` / `SelectObject` 要成对释放，见 `LayeredSurface.Release()`。 |
| 重绘时机 | 数据更新、外形切换、透明度/色调变更、窗口尺寸变化。**没有动画时一次都不重绘**，这就是空闲 CPU≈0 的原因。 |

### 4.3 球面的画法（纯 GDI+，无贴图）

从后往前五层：

1. **外投影**：由外向内叠 15 个同心圆，alpha 按 `(1-t)^2.2` 衰减 —— 不用模糊也能出软边；
2. **球体主光**：`PathGradientBrush` + `CenterPoint` 偏左上 + `FocusScales=0.06`，做出「亮面→暗面」的球面过渡；
3. **边缘压暗**：同一路径再来一层 `PathGradientBrush`，`CenterColor` 全透明、`SurroundColors` 深黑、`FocusScales=0.60`，只压边不压心；
4. **镜面高光**：左上一个小椭圆，中心白 alpha≈90 → 边缘 0；
5. **数字衬底**：数字底下再压一团暗色径向渐变（alpha≈115），保证任何桌面壁纸上数字都可读；数字本身再画一遍 1px 暗影。

外层进度环用 `DrawArc` + `LineCap.Round`：外环=本月已用，内弧（更细、更靠近圆心）=5 小时窗口。

### 4.4 文字排版的两个硬规则

- **中文必须用 `Microsoft YaHei UI`**。`Segoe UI` 没有 CJK 字形，直接画出来是方块（实测「重置」变成两个豆腐块）。
- **测量与绘制必须同一种 `StringFormat`**。用 `GenericTypographic` 测出的宽度比 `DrawString` 实际排版宽度小约 10px，按测量宽度给矩形会**逐字截断**（「92」只出「9」）。现在统一：普通 `MeasureString` 取宽，绘制用 `Alignment=Near` + 富余 20–28px 的矩形。

## 五、交互状态机

### 5.1 悬停

用一个 110ms 的 `WinTimer` 轮询 `Cursor.Position`（不是靠 `MouseEnter`）：

```
光标在"可见区"(不含投影留白) 或 详情面板内
   → 记录 _lastIn；若已停留 >170ms 且面板未显示 → ShowDetail()
光标离开
   → 若面板可见且已离开 >420ms → HideDetail()
```

为什么用轮询：拖动、菜单、多窗口之间穿梭时，`Enter/Leave` 事件会漏（尤其分层窗口 + 置顶窗口切换），轮询最稳，代价是每秒 9 次 `GetCursorPosition`，可以忽略。

### 5.2 菜单与置顶的冲突

这里有个必须处理的顺序问题：菜单是普通弹出窗口，而悬浮窗/详情面板都是 `TopMost`——**不改的话菜单会被自己的面板压住**。所以菜单打开时：

1. `Opening`：`HideDetailForce()`（无视「常显」设置强行收面板）+ `_menuDepth++`；
2. `Opened`：对菜单窗口自己 `SetWindowPos(HWND_TOPMOST)`；
3. 菜单开着期间，**暂停**那个 1.5 秒的顶层重申（否则它会把自己重新顶到菜单上面）；
4. `Closed`：`_menuDepth--` 并恢复顶层重申。

### 5.3 贴边吸附与「留白悖论」

窗口比可见图形大一圈（球形 55px 图形 + 18px 投影留白）。如果按窗口边界钳到工作区，可见球离屏幕边就有 18px，看着「浮在中间」。做法：吸附时**允许窗口向屏幕外探出 2/3 留白**，可见图形离边只剩 1/3（球 6px、条 4px），既贴边又不会切到投影。

## 六、数据管道与失败降级

```
Poller 线程（独立，IsBackground）
  ├ 每次请求前保证距上次 ≥2.5s（服务端限速 1 次/秒）
  ├ HttpWebRequest（15s 超时、TLS1.2、Bearer 只读 key）
  ├ JavaScriptSerializer → Snapshot（整体新建，不做增量）
  └ Outcome{ State, Snap, Message } → AppHost.BeginInvoke → 应用到 UI
```

`NetState` 与退避策略（这是「不刷屏、不打扰」的落点）：

| 状态 | 触发 | 界面表现 | 下次重试 |
|---|---|---|---|
| Ok | 200 且解析成功 | 正常 | 300s（可配） |
| Network | 超时 / 断网 / 其他异常 | 保留旧值 + 状态点 + 离线 | 60s |
| Unauthorized | 401 | 红点 +「钥匙失效」 | 600s |
| Forbidden | 403 | 「接口拒绝」 | 600s |
| RateLimited | 429 | 保持旧值 +「限流退避」 | 8s |
| GatewayOff | 503 | 「网关已关闭」 | 120s |
| HttpError | 其它 4xx/5xx、解析失败 | 「接口错误」 | 120s |
| NoKey | 未配置 key | 首次弹输入框 | 30s |

界面更新只走 `BeginInvoke` 到 UI 线程；轮询线程从不碰控件。

## 七、配置与持久化

数据目录**逐级探测可写位置**，用第一个能真正写进去的（探测方式是建目录 + 写探针文件 + 删除）：

1. `%APPDATA%\GWQuota\`
2. `%LOCALAPPDATA%\GWQuota\`
3. `exe 同目录\data\`（便携回退）

这样即使装在 Program Files、或所在用户被策略限制写漫游目录，程序也不会「设置记不住」。

三个文件：

- `key.txt` —— 只读 key，纯文本，永不进 exe 资源段；查找顺序是「数据目录 → %APPDATA% 标准位 → exe 同目录」。
- `config.ini` —— 手写 key=value（不引 JSON 库，出错也不至于整个配置读不出来）：`form / x / y / opacity / hue / sat / palette / warn / interval / preview / trayhint`。
- `gwquota.log` —— 只记错误与关键注册结果，>200KB 自动重建，**不含 key**。

## 八、性能

| 指标 | 实测 |
|---|---|
| 常驻内存 | 40–42 MB |
| 空闲 CPU | 计时器每 1.5s 一次 `SetWindowPos`（微秒级），无重绘时接近 0 |
| 峰值 CPU | 一次球体重绘（15 层阴影 + 3 层渐变 + 文字）< 2ms |
| 网络 | 5 分钟一次 GET，请求体 0，响应约 4KB |
| 磁盘 | 仅在配置变更/移动时写 ini |

## 九、如果重做，会改什么

1. **拆文件**：2900 行单文件编译方便，但改动定位靠 grep；正常项目应按 类型/层 拆 8–10 个文件。
2. **引入 `async/await`**：现在是 `HttpWebRequest` 同步 + 后台线程，逻辑直白，但换 `.NET 6` 的话应该用 `HttpClient` 异步。
3. **JSON 手写解析**：`JavaScriptSerializer` 够用，但字段容错（类型可能变）全靠 `J.Num/J.Bool` 这类辅助方法，量再大就该用 `System.Text.Json` 或 Source Generator。
4. **托盘**：应当一开始就做「原生 `Shell_NotifyIcon` + 自建消息窗口」，而不是依赖 `NotifyIcon` 封装，排查问题时可控性会好很多（本次已验证是系统侧问题，但封装层不透明确实拖慢了定位）。
